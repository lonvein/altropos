# Клим — капитан, RAG и интеграция

## Цель и зона ответственности

Собрать навигатор по регламентам МФТИ: вопрос → гибридный поиск → понятный ответ → проверка утверждений → ссылки на основания. Ты отвечаешь за RAG, локальные модели, общий контракт данных, стыковку компонентов и окончательное слияние изменений команды.

Репозиторий: https://github.com/lonvein/altropos. Рабочая ветка: `feature/rag`. Егор ведёт документы и импорт, Глеб — интерфейс, развёртывание и демонстрацию. Работаем в течение двух дней; часы ниже отсчитываются от старта командной работы.

## Что сделать в первую очередь

1. В первые два часа согласовать с Егором и Глебом структуры ниже. Зафиксировать их в `navigator/schemas.py` и коротком примере запроса/ответа. До готовности моделей дать Глебу явно обозначенный тестовый ответ для разработки интерфейса.
2. Проверить SSH к A100, объём памяти, доступность GPU и возможность запуска модели. Вместе с Глебом проверить резервную 3060 Ti. Не ждать завершения парсеров: начать с искусственного документа.
3. Поднять сервис embeddings/reranker и LLM. Передать Глебу адреса, параметры запуска, названия и точные ревизии моделей; секреты передавать отдельно от Git.
4. Реализовать индексирование, затем поиск и только после него генерацию и проверку ответа.

## Задачи

### Обязательные

- Лексический поиск: `rank-bm25`, нормализация русского текста и словарь сокращений. Не терять даты и номера приказов.
- Метрический поиск: `BAAI/bge-m3`, нормализованные векторы размерности 1024, FAISS. Сохранение и загрузка индекса, проверка fingerprint embedding-модели и её ревизии.
- Поиск по исходному вопросу и, для составных запросов, максимум трём подзапросам. При недоступности модели использовать исходный вопрос.
- До 30 результатов от каждого поисковика на запрос; объединение RRF с константой 60; reranker `BAAI/bge-reranker-v2-m3` для максимум 40 уникальных кандидатов.
- Получение родительских условий, продолжений процедуры и подтверждённых поправок. Учитывать дату запроса и подтверждённые периоды действия. Поздняя дата сама по себе не отменяет предыдущий документ.
- Генерация структурированного ответа. У каждого существенного утверждения и шага должны быть `fragment_id` и дословная цитата.
- Программная проверка JSON, идентификаторов и наличия цитат. Затем отдельный последовательный вызов той же модели для проверки смысла, условий, исключений и полноты.
- Одна попытка исправления; затем только проверенные выдержки и сообщение об ограничении. Не выдавать неполную процедуру за полный порядок действий.
- Ограниченные режимы: без LLM доступны поиск и источники; без embeddings/reranker работает BM25 с явным предупреждением. Не переключаться между машинами автоматически.
- Защита инструкции модели: документы — источник данных, команды внутри них не меняют правила поведения системы.
- API `POST /api/ask`; временные метрики поиска/генерации и понятные ошибки.

### Профили моделей

| Параметр | A100 | 3060 Ti | Облегчённый резерв |
|---|---|---|---|
| LLM | Qwen2.5-14B-Instruct GGUF Q4_K_M | Qwen3-8B GGUF Q4_K_M | Qwen3-4B GGUF Q4_K_M |
| Контекст | 16384 | 4096 | 4096 |
| Материалы, максимум токенов | 8000 | 2200 | 2200 |
| Ответ, максимум токенов | 1536 | 768 | 768 |
| Найденные фрагменты, максимум | 8 | 4 | 4 |
| Embeddings/reranker | GPU | CPU | CPU |

Qwen3 запускается без thinking mode. Один активный запрос к LLM; генерация и проверка используют одну загруженную модель последовательно. Полный запрос вместе с инструкциями, источниками и резервом ответа должен помещаться в контекст. При нехватке места явно сообщать об ограничении. Не обещать, что 8B поместится на конкретной машине, до проверки.

## Стыковка с Егором

Егор владеет извлечением и разбиением документов. Он передаёт фрагменты с полями:

```json
{
  "id": "стабильный идентификатор фрагмента",
  "document_id": "идентификатор документа",
  "ordinal": 0,
  "text": "текст пункта с необходимыми заголовками",
  "section": "3.2",
  "locator": {"kind": "pdf", "page": 2, "bbox": [0, 0, 100, 100]}
}
```

Варианты locator: PDF — `page` с единицы и необязательный `bbox`; DOCX — `block` с нуля; XLSX — `sheet` и `range`; HTML — `block` с нуля. В SQLite locator сериализуется в JSON. Фрагменты со стабильными ID используются и поиском, и просмотрщиком; изменение содержимого создаёт новую версию.

Предоставить Егору функцию `index_document(document_id, fragments) -> IndexResult`. Она публикует фрагменты и индекс согласованно; возвращает `mode: hybrid | bm25` и предупреждения. При ошибке публикации документ не получает статус `ready`. Повторная обработка не должна создавать дубликаты. В BM25-режиме отсутствие векторов фиксируется явно; после восстановления ML предусматривается переиндексирование.

Егор сохраняет подтверждённые метаданные и связи документов; ты используешь их при поиске. Если данных для выбора редакции недостаточно, ответ должен содержать предупреждение, а спорный вывод не публикуется как окончательный.

## Стыковка с Глебом

Вход `POST /api/ask`: `question` и необязательная дата `as_of` в формате YYYY-MM-DD. Ответ:

```json
{
  "status": "partial",
  "summary": [{"text": "Подтверждённый вывод", "evidence": [{"fragment_id": "f1", "quote": "Дословная выдержка"}]}],
  "steps": [],
  "sources": [{"fragment_id": "f1", "document_id": "d1", "title": "Учебный документ", "locator": {"kind": "pdf", "page": 2}, "url": "/api/sources/f1"}],
  "warnings": ["Не хватает информации для полного ответа"],
  "clarification": null
}
```

Пример искусственный. Допустимые статусы: `answered`, `partial`, `not_found`, `ambiguous`, `conflict`, `unavailable`. `summary` и `steps` — списки утверждений одной структуры. Названия документов и URL добавляет сервер по базе, а не придумывает модель. Не добавлять неподтверждённые советы в свободный текст.

Отдать FastAPI-router для подключения Глебом в `navigator/main.py`. Интерфейс не должен зависеть от названия модели или профиля.

## Владение файлами и интеграция

Твоя зона: `navigator/rag/`, `services/ml/`, общие `navigator/config.py`, `navigator/schemas.py`, `navigator/db.py`, `navigator/text.py`, зависимости и тесты RAG. Уже начатые локальные файлы — черновой каркас, а не готовая реализация; перед публикацией проверить их совместно с командой.

Глеб владеет `navigator/main.py`, интерфейсом и Docker; Егор — `navigator/ingestion/`, `navigator/documents/` и тестами обработки. Изменения общих схем и зависимостей проходят через тебя, чтобы избежать конфликтов.

- Первые 2 часа: контракты, доступы, примеры данных и назначение работ.
- До конца первого дня: принять вертикальный сценарий «один документ → поиск → ответ → открытие источника».
- Второй день: несколько документов, редакции, отказы, резервный профиль и финальные проверки.
- Последние 3–4 часа: прекратить добавление функций, исправить критические ошибки, проверить чистый запуск, записать демонстрацию.

Каждый работает в своей ветке, делает небольшие коммиты и PR. Только ты сливаешь в `main`, после просмотра и проверки. Не откладывать всю интеграцию на вечер второго дня. Блокеры по доступам, схемам и API сообщать команде сразу.

## Критерии готовности

- По размеченным вопросам найдены нужные основания; измерены Recall@8 для A100 и Recall@4 для резерва, цель — не менее 90% на вопросах с ответом.
- Все существенные опубликованные утверждения подтверждены существующими цитатами; отсутствие ответа и конфликты обработаны явно.
- Протестированы неверный JSON, недоступность моделей, вставка инструкций в документ и недостаток контекста.
- Два профиля проходят общий набор проверок; если оборудование недоступно, это записано как непроверенное, без выдуманных результатов.
- Есть раздел архитектуры RAG и ограничений для README, описание моделей и таблица фактических результатов.
- На защите ты объясняешь бизнес-сценарий, архитектуру, достоверность и объединяешь выступления команды.

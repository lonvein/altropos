# Глеб — веб-интерфейс, развёртывание и демонстрация

## Цель и зона ответственности

Сделать прототип удобным и воспроизводимым: сотрудник задаёт вопрос и видит ответ с основаниями; администратор добавляет документы; другой человек запускает приложение по README.

Репозиторий: https://github.com/lonvein/altropos. Рабочая ветка: `feature/web-deploy`. Клим реализует RAG, модели и интеграцию; Егор — документы, очередь, источники и импорт. Срок — два дня.

## Первый результат

В первые два часа согласуй с Климом JSON ответа и с Егором состояния загрузки. Начни интерфейс на явно обозначенных искусственных ответах. Тестовые заглушки не должны оставаться в рабочем режиме или выдаваться за результат модели.

К концу первого дня нужен работающий сценарий: загрузить документ → дождаться обработки → задать вопрос → открыть источник. Оформление улучшать после появления этого пути.

## Задачи по интерфейсу

### Страница «Задать вопрос»

- Поле вопроса, необязательная дата применимости, кнопка отправки, состояние ожидания.
- Краткий ответ и нумерованные шаги. Каждый вывод показывает ссылки на подтверждения; по нажатию открываются документ и дословная цитата.
- Отдельно показывать предупреждения, частичный ответ, противоречие, отсутствие информации и уточняющий вопрос.
- Не показывать технические оценки релевантности как вероятность правильности. Не называть частичный ответ полной инструкцией.
- Обрабатывать пустой запрос, тайм-аут, отказ модели и сетевую ошибку; сохранять введённый вопрос. Повторная отправка не должна происходить незаметно.
- Выводимый текст экранировать; не вставлять ответ модели через небезопасный `innerHTML`.

### Страница «Документы»

- Загрузка PDF/DOCX/XLSX, список документов и опрос состояния задания.
- Состояния `queued`, `processing`, `ready`, `needs_review`, `error` с понятными русскими подписями.
- Импорт URL официального сайта: предварительная загрузка страницы, список найденных разрешённых документов, выбор связанных файлов для импорта.
- Просмотр и редактирование метаданных: название, номер, даты действия и подтверждение связей изменений. Не подтверждать автоматически предложенные связи.
- Просмотр оригинала PDF на нужной странице; для DOCX/XLSX/HTML — представление Егора с адресуемыми блоками и выделением.

Технологии: FastAPI, Jinja2, HTML/CSS и небольшой JavaScript. Отдельную сборку React и многоходовую память чата не добавлять.

## Контракты, на которые опираться

`POST /api/ask` принимает `question` и необязательный `as_of` в формате YYYY-MM-DD. Клим возвращает:

```json
{
  "status": "partial",
  "summary": [{"text": "Подтверждённый вывод", "evidence": [{"fragment_id": "f1", "quote": "Дословная выдержка"}]}],
  "steps": [],
  "sources": [{"fragment_id": "f1", "document_id": "d1", "title": "Учебный документ", "locator": {"kind": "pdf", "page": 2}, "url": "/api/sources/f1"}],
  "warnings": ["Не хватает информации для полного ответа"],
  "clarification": null
}
```

Пример искусственный. Допустимые статусы: `answered`, `partial`, `not_found`, `ambiguous`, `conflict`, `unavailable`. `summary` и `steps` — списки утверждений одинаковой структуры. Связывай evidence с sources по `fragment_id`; не придумывай ссылку или название на клиенте.

Backend документов реализует Егор:

| Endpoint | Результат |
|---|---|
| `POST /api/documents` | Multipart-файл → `document_id`, `job_id`, `status` |
| `POST /api/import-url` | `{url, selected_urls: []}` → `job_id`; результат задания содержит допустимые ссылки и ID документов |
| `GET /api/jobs/{id}` | `id`, `status`, `error`, `result` |
| `GET /api/documents` | `{documents: [...]}` |
| `PATCH /api/documents/{id}/metadata` | Обновление метаданных и подтверждение связей |
| `GET /api/sources/{fragment_id}` | HTML-представление источника |
| `GET /api/documents/{id}/original` | Оригинальный файл |

Минимальная запись документа: `id`, `title`, `status`, `warnings`, `metadata`. Ошибки API — поле `detail`. Точные Pydantic-схемы утверждает Клим; подключай routers Клима и Егора в принадлежащем тебе `navigator/main.py`.

Ты реализуешь `GET /health`: активный профиль, состояние приложения/ML/LLM и причины ограниченного режима. Недоступность модели не должна делать страницу или просмотр документов недоступными.

## Docker и профили оборудования

Три сервиса Compose: приложение, embeddings/reranker, LLM. Названия адресов и портов согласуй с Климом; внутри контейнера `127.0.0.1` не указывает на соседний сервис. Модельные сервисы не публиковать в интернет. Веб-приложение — на localhost, для A100 доступ через SSH-туннель.

| Настройка | A100 | 3060 Ti | Облегчённый резерв |
|---|---|---|---|
| LLM | Qwen2.5-14B-Instruct GGUF Q4_K_M | Qwen3-8B GGUF Q4_K_M | Qwen3-4B GGUF Q4_K_M |
| Контекст | 16384 | 4096 | 4096 |
| Бюджет материалов | 8000 | 2200 | 2200 |
| Максимум ответа | 1536 | 768 | 768 |
| Фрагментов | 8 | 4 | 4 |
| Embeddings/reranker | GPU | CPU | CPU |

- Профиль задаётся конфигурацией без изменения кода. Qwen3 — без thinking mode; один запрос к LLM одновременно.
- Проверить на доступном оборудовании память и реальный запрос. Если 8B не помещается, переключить на 4B; не обещать скорость и качество без испытания.
- Системные зависимости: Tesseract rus+eng и зависимости PDF-рендера по списку Егора. Версии Python, библиотек, `llama.cpp` и ревизии весов зафиксировать совместно с Климом.
- `.env.example` не содержит секретов. Веса скачиваются отдельной документированной командой и монтируются в контейнер; не класть их в Git или образ приложения.
- Сохранять `runtime` в постоянном volume. Образы не должны требовать исходных внутренних файлов из папки разработчика.
- Проверить чистый запуск и остановку по инструкции. Если Docker или GPU недоступны, явно записать непроверенные пункты.
- Подготовить резервное копирование и восстановление: остановить приложение, перенести SQLite, документы и индексы единым снимком. Fingerprint embedding-модели проверяет код Клима. Не копировать живую SQLite-базу без согласованного снимка.
- Для GitHub подготовить CI только на искусственных данных, без GPU и скачивания многогигабайтных моделей: установка зависимостей и запуск тестов команды. Это не заменяет проверку на A100/3060 Ti.

## Проверка, README и демонстрация

Собрать общий набор из 40 вопросов: 12 на один документ, 8 составных, 6 без достаточного ответа, 6 редакций/конфликтов, 4 OCR, 4 таблицы. Включить перефразирования.

Егор готовит 12 примеров: 4 OCR, 4 таблицы, 4 редакции. Ты готовишь остальные 28: 12 одиночных, 8 составных, 6 без ответа, 2 конфликта. Клим проверяет разметку и реализует измерение поиска/подтверждённости. Деление 20/20 на настройку и итоговую проверку сделать заранее, сохранив разные категории в обеих частях. Если нужны искусственные документы, помечать их явно.

- Проверить интерфейс на всех статусах, корректность ссылок и повторную загрузку страницы.
- Провести сквозные проверки со всей командой и оформить фактические результаты отдельно для A100 и 3060 Ti. Не подставлять результаты заглушек вместо модели.
- README: требования к ОС/RAM/GPU, установка, получение весов, настройки профилей, запуск/остановка, SSH-туннель, загрузка документов, перенос базы, ограничения и минимум два сценария с ожидаемым результатом.
- Архитектуру RAG и моделей предоставляет Клим, описание обработки файлов — Егор; ты собираешь общую документацию.
- Записать видео: обычный вопрос → несколько источников → нехватка данных → загрузка нового документа → открытие подтверждения. Убрать секреты и непредназначенные для публикации сведения.
- Для защиты подготовить компактные слайды или сценарий показа; Клим утверждает итоговый рассказ и выступает капитаном.

## Владение файлами и порядок работы

Твоя зона: `navigator/main.py`, общие шаблоны и статические файлы интерфейса, Dockerfile/Compose, примеры окружения, скрипты запуска/переноса, CI, README, сквозные тесты и материалы демонстрации. HTML содержимого источников делает Егор; ты отвечаешь за его оформление и встраивание.

Общие `config.py`, `schemas.py`, `db.py` и зависимости принадлежат Климу: изменения согласовывай, не редактируй их одновременно с ним.

Работай небольшими коммитами в `feature/web-deploy`, PR передавай Климу. В `main` сливает капитан. Блокеры по API и окружению сообщай сразу.

## Критерии готовности

- Обе страницы работают с настоящими API, подтверждения открываются, ограничения заметны пользователю.
- Приложение запускается по README без ручного исправления кода; данные переживают перезапуск.
- В конфигурации есть A100, 3060 Ti и 4B; фактически непроверенные варианты помечены.
- Проверены перенос базы и отсутствие внутренних документов, секретов и весов в составе коммита.
- Готовы общий набор вопросов, таблица результатов, минимум два use case и видео рабочего прототипа.

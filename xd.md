# Навигатор по регламентам МФТИ с основным запуском на A100 и резервным на RTX 3060 Ti

## 1. Назначение и результат

Создаём веб-приложение, которое находит ответы в регламентах МФТИ и объясняет сотруднику порядок действий.

Основа — **гибридный RAG**: поиск одновременно по словам и смысловой близости, затем формирование ответа локальной моделью и проверка утверждений по найденным источникам.

Пользователь получает:

1. Краткий ответ простым языком.
2. Пошаговый порядок действий, если он описан в документах.
3. Подтверждающие цитаты и ссылки на конкретные фрагменты.
4. Предупреждение о противоречиях, неоднозначности или нехватке информации.

Администратор может загружать PDF, DOCX и XLSX, импортировать материалы официального сайта и уточнять связи редакций.

**Результат за два дня:** рабочий прототип на предоставленном комплекте документов, два профиля запуска, проверочные примеры, документация и запись демонстрации.

Гарантию отсутствия любых смысловых ошибок не заявляем. Реализуем проверяемость каждого существенного утверждения и консервативный отказ от неподтверждённых ответов.

## 2. Архитектура и два профиля оборудования

### Общие компоненты

| Компонент | Выбранное решение |
|---|---|
| Приложение | Python 3.11, FastAPI, Pydantic |
| Веб-интерфейс | Jinja2, HTML/CSS, небольшой JavaScript |
| Метаданные и очередь обработки | SQLite |
| Оригиналы и извлечённые материалы | Файловое хранилище |
| Лексический поиск | BM25 через `rank-bm25` |
| Метрический поиск | `BAAI/bge-m3` и FAISS |
| Повторное ранжирование | `BAAI/bge-reranker-v2-m3` |
| Генерация и смысловая проверка | Qwen через `llama.cpp` |
| Развёртывание | Docker Compose |

Три сервиса: приложение с обработкой документов, сервис embeddings/reranker и языковая модель. BM25 и FAISS работают внутри приложения.

**Поток данных:**

```text
Файлы / официальный сайт
        ↓
Извлечение текста, структуры и таблиц
        ↓
Фрагменты с указанием происхождения
        ↓
BM25 + векторный индекс

Вопрос
  ↓
Гибридный поиск
  ↓
Повторное ранжирование
  ↓
Добавление условий, продолжений и поправок
  ↓
Генерация ответа
  ↓
Проверка утверждений и цитат
  ↓
Ответ / уточнение / сообщение о нехватке данных
```

### Профили запуска

| Настройка | Основной — A100 | Резервный — RTX 3060 Ti |
|---|---|---|
| Генеративная модель | Qwen2.5-14B-Instruct, GGUF Q4_K_M | Qwen3-8B, GGUF Q4_K_M |
| Контекст модели | 16 384 токена | 4 096 токенов |
| Бюджет исходных материалов | До 8 000 токенов | До 2 200 токенов |
| Максимальный ответ модели | 1 536 токенов | 768 токенов |
| Embeddings и reranker | GPU | CPU |
| Одновременная генерация | Один запрос | Один запрос |
| Генерация и проверка | Последовательно | Последовательно |
| Облегчённая модель | Не требуется | Qwen3-4B, GGUF Q4_K_M |

Для резервного профиля используем Qwen3 без thinking mode. Официальные файлы Q4_K_M занимают около 5,03 ГБ для 8B и 2,50 ГБ для 4B; дополнительно нужна память для контекста и вычислений. Поэтому возможность полного размещения 8B на GPU проверяем практически. [Qwen3-8B](https://huggingface.co/Qwen/Qwen3-8B-GGUF/tree/main), [Qwen3-4B](https://huggingface.co/Qwen/Qwen3-4B-GGUF/tree/main)

При нехватке памяти на 3060 Ti переключаемся на 4B с тем же контекстом. Автоматическую выгрузку слоёв на CPU в базовый профиль не включаем: для демонстрации предпочитаем предсказуемую конфигурацию.

Профиль выбирается через конфигурацию без изменения исходного кода. Он задаёт модель, устройство embeddings/reranker и бюджеты контекста. Версии библиотек, сборка `llama.cpp` и ревизии весов фиксируются.

**Переход между машинами:** переносим хранилище документов, SQLite и индексы единым снимком при остановленном приложении. Поскольку embedding-модель и её ревизия одинаковы, повторное индексирование не требуется. Проверяем совместимость индекса по сохранённым параметрам модели.

Основной сервер доступен через SSH-туннель. Резервный профиль запускается целиком на компьютере с 3060 Ti. Внешние AI-провайдеры не используются.

## 3. Документы, поиск и достоверность

### Обработка документов

- **PDF:** `pdfplumber` для текста и таблиц; Tesseract с русским и английским языками для страниц без пригодного текстового слоя. Сохраняем страницы и координаты блоков.
- **DOCX:** `python-docx`; сохраняем порядок абзацев, заголовков, списков и таблиц.
- **XLSX:** `openpyxl`; сохраняем листы, диапазоны, заголовки, формулы и доступные сохранённые значения. Формулы не пересчитываем; отсутствие результата обозначаем.
- Повторную загрузку определяем по хешу. Ошибка одного файла не останавливает обработку остальных.
- Очередь обрабатывает один документ за раз; состояния заданий сохраняются в SQLite. После перезапуска незавершённое задание запускается заново.
- Документ включается в поиск только после успешного завершения индексирования.

Единица поиска содержит текст, идентификатор документа, редакцию, заголовок, пункт и местоположение в оригинале.

Начальное разбиение: около 500 токенов, максимум 800, перекрытие 80 токенов для длинных разделов. Списки и короткие пункты сохраняем целиком. Таблицы делим группами строк с повторением заголовков.

### Редакции и официальный сайт

Сохраняем номер документа, дату издания, известные даты действия и связи «изменяет», «отменяет», «приложение к».

Автоматически извлечённые связи изменений требуют подтверждения администратора. Поздняя дата сама по себе не означает отмену предыдущего документа. Поправки извлекаем вместе с затронутыми пунктами. Если актуальность неизвестна, показываем это пользователю.

Импорт сайта выполняется по указанному URL с домена `mipt.ru` или его поддоменов. Загружаем основное содержание страницы и выбранные пользователем связанные документы, сохраняем URL, дату получения и снимок содержимого. Перенаправления проверяются по тому же списку разрешённых адресов.

Полный обход сайта в первую версию не входит.

### Гибридный поиск

1. Нормализуем вопрос, сохраняя даты, номера приказов и сокращения; используем пополняемый словарь терминов МФТИ.
2. Для составного вопроса модель выделяет до трёх подзапросов. Исходный вопрос также участвует в поиске.
3. По каждому запросу получаем до 30 кандидатов из BM25 и до 30 из FAISS.
4. Объединяем результаты по RRF — сумме обратных рангов с константой 60.
5. Повторно ранжируем до 40 уникальных кандидатов.
6. Выбираем до восьми фрагментов на A100 и до четырёх на 3060 Ti, добавляя необходимые условия и связанные поправки в пределах бюджета.

Для резервного профиля контекст собираем из подтверждающих абзацев и необходимых соседних условий. Если процедура не помещается целиком, не обрезаем её молча: выдаём частичный ответ с предупреждением либо предлагаем уточнить вопрос.

Уверенность не представляем как процент вероятности правильности. Порог допуска кандидатов настраиваем на размеченных примерах и фиксируем в конфигурации.

### Генерация и проверка

Модель получает вопрос и материалы с идентификаторами источников. Возвращает JSON: краткий ответ, шаги, предупреждения и подтверждающие цитаты для каждого утверждения.

Проверяем:

- корректность структуры JSON;
- существование указанных источников;
- наличие цитат в извлечённом тексте;
- соответствие смысла утверждений источникам;
- сохранность сроков, ролей, условий и исключений;
- полноту процедуры в доступном контексте.

Смысловую проверку выполняет отдельный вызов той же загруженной модели. Это дополнительный фильтр, а не независимое доказательство правильности.

Допускается одна попытка исправления. Если ответ повторно не проходит проверку, показываем подтверждённые выдержки и объясняем ограничение. Неполную последовательность не называем полным порядком действий.

Документы считаются данными: инструкции внутри них не должны менять поведение системы. Проверку на такие вставки включаем в тестирование.

При недоступности LLM остаются поиск и просмотр источников. При недоступности embeddings/reranker остаётся BM25 с явным обозначением ограниченного режима. Автоматического переключения между удалённым сервером и локальным компьютером нет.

## 4. Интерфейсы и последовательность реализации

### Веб-интерфейс и API

Две страницы:

- **«Задать вопрос»:** вопрос, ответ, шаги, предупреждения, уточнения и источники.
- **«Документы»:** загрузка, импорт URL, состояния обработки и подтверждение метаданных редакций.

PDF открывается на нужной странице с подтверждающим текстом рядом. Для DOCX и XLSX создаются HTML-представления с адресуемыми абзацами и диапазонами.

| Интерфейс | Назначение |
|---|---|
| `POST /api/documents` | Загрузка файла |
| `POST /api/import-url` | Импорт официального источника |
| `GET /api/jobs/{id}` | Состояние обработки |
| `GET /api/documents` | Список документов и редакций |
| `PATCH /api/documents/{id}/metadata` | Подтверждение метаданных и связей |
| `POST /api/ask` | Вопрос и необязательная дата применимости |
| `GET /api/sources/{fragment_id}` | Подтверждающий фрагмент |
| `GET /health` | Состояние компонентов и активный профиль |

Ответ `/api/ask` содержит статус `answered`, `partial`, `not_found`, `ambiguous`, `conflict` или `unavailable`; краткий ответ; шаги с подтверждениями; источники; предупреждения; при необходимости уточняющий вопрос.

Первая версия обрабатывает самостоятельные вопросы. Многоходовая память диалога, корпоративная авторизация, права по подразделениям и вычисление смет в неё не входят.

### Порядок работ на два дня

| Этап | Работа | Проверяемый результат |
|---|---|---|
| 1. Проверка окружения | Поднять модели и Compose на A100; проверить 8B и 4B на 3060 Ti | Оба профиля выполняют пробный запрос без ошибки памяти |
| 2. Документы | Парсеры, OCR, происхождение фрагментов, просмотр источников | Файлы обработаны либо имеют объяснённую ошибку |
| 3. Поиск | BM25, FAISS, RRF и reranker | Найдены основания для контрольных вопросов |
| 4. Ответы | JSON-контракт, генерация, проверки и ограниченные режимы | Каждый опубликованный вывод связан с источником |
| 5. Полный сценарий | Импорт URL, редакции, обработка сбоев | Работает путь от загрузки до ответа |
| 6. Перенос и сдача | Снимок базы, проверка резервного запуска, README и видео | Прототип воспроизводится на второй машине |

Сначала собираем основной сквозной сценарий. Резервное оборудование проверяем в начале, а полный перенос базы — перед финальной демонстрацией.

Распределение блоков между тремя участниками выполняется следующим шагом.

## 5. Проверка качества и комплект сдачи

Готовим 40 размеченных вопросов: 12 с ответом в одном документе, 8 составных, 6 без достаточного ответа, 6 на редакции и конфликты, 4 на OCR и 4 на таблицы. Включаем перефразированные формулировки.

Для каждого примера указываем ожидаемые источники, обязательные факты и допустимый статус. Половину используем для настройки, половину — для итоговой проверки.

Проверяем оба профиля на одном наборе:

- Целевой Recall@8 для A100 и Recall@4 для 3060 Ti — не менее 90% на вопросах с ответом. Для составных вопросов отдельно проверяем наличие всех необходимых оснований.
- Все опубликованные существенные утверждения имеют рабочие ссылки и подтверждения.
- На итоговом наборе ручная проверка не обнаруживает неподтверждённых утверждений.
- Проходят проверки отсутствующего ответа, конфликтов и неполной процедуры.
- Уменьшение контекста резервного профиля не приводит к молчаливой потере обязательных шагов.
- Обрабатываются повреждённые файлы, пустые запросы, неверный JSON, тайм-ауты, отсутствие модели и попытки передать инструкции через документ.
- Новый документ добавляется без изменения кода; база сохраняется после перезапуска и переноса.
- Чистый запуск проходит по README.

Если 8B не проходит проверки памяти или качества, резервным становится профиль 4B после того же набора проверок. Если качество связного ответа недостаточно, резервный профиль публикует только проверенные выдержки.

Измеряем время индексирования, поиска и полного ответа отдельно для двух машин. Ориентир для A100 — обычный ответ до 60 секунд после прогрева; для 3060 Ti фиксируем фактические результаты без обещания той же скорости.

**Комплект сдачи:** Dockerfile/Compose, профили A100/3060 Ti/4B, `.env.example`, зафиксированные зависимости и ревизии моделей, инструкция получения весов, README, архитектура, результаты проверки, инструкция переноса базы и видео демонстрации.

В GitHub автоматически не включаем секреты, веса и внутренние документы. Для воспроизводимых примеров используем разрешённые материалы или явно обозначенные искусственные документы.

**Допущения:** A100 разрешена для обработки материалов; доступен Docker с NVIDIA runtime; резервная 3060 Ti имеет стандартные 8 ГБ видеопамяти; на резервном компьютере желательно 32 ГБ RAM, а пригодность машины с меньшим объёмом проверяется на первом этапе. Веса можно скачать заранее; во время ответов внешние AI-сервисы не нужны.

Исходные регламенты пока не предоставлены в рабочую папку. Их фактический состав и качество проверяем до настройки поиска. Масштаб 600–700 документов предусматриваем архитектурно, но подтверждаем только отдельным испытанием.

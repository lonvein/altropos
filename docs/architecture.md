# Архитектура altropos

Основа следует распределению работ в заданиях команды. Это техническое предложение
для совместной разработки; фактическое согласование участниками выполняется при review PR.

```text
Егор: файлы / разрешённые URL → очередь SQLite → извлечение → Fragment[]
Клим: index_document → неизменяемые файлы индекса → Store.publish → ready
Глеб: POST /api/ask → router Клима → поиск → генерация → проверка → AskResponse
                                     ↓                             ↓
                              ready-публикации              sources по базе
```

Один FastAPI-процесс, одна SQLite-база в DATA_DIR, оригиналы и индексы рядом.
Егор и Клим передают routers Глебу для подключения в `navigator/main.py`.
Нативные форматы, OCR, импорт сайта и очередь — отдельная реализация Егора.
ML-сервис embeddings/reranker и локальный OpenAI-compatible LLM-сервер
вызываются через типизированные адаптеры `navigator/interfaces.py`.
Транспорт ML не зафиксирован как уже работающий endpoint; клиент скрывает его от RAG.

## Публикация и хранение

Документ обозначает неизменяемую версию исходного файла. Повтор SHA-256 возвращает
существующий ID; изменённый файл получает новые document ID, version и fragment ID.
Подтверждённые поправки связываются метаданными, не заменяют старый документ молча.
PDF bbox задан в пунктах от левого верхнего угла страницы; координаты преобразует парсер.

Будущий индексатор — единственный писатель индексов. Для каждого документа он готовит
шард BM25 и при наличии ML — шард FAISS в `indexes/<publication_id>/`.
Фрагменты сортируются по ordinal, их канонический JSON хешируется.
Файлы сначала пишутся во временный каталог на той же файловой системе,
сбрасываются на диск, затем переименовываются в окончательный каталог.
После этого Store проверяет пути, хеши и версии. В одной `BEGIN IMMEDIATE`
транзакции сохраняются манифест, снимок фрагментов, активные фрагменты и ready-указатель.
При сбое старый указатель сохраняется; новая версия не становится ready.
Незавершённые файлы остаются сиротами и удаляются только отдельной будущей процедурой.
Файлы опубликованного каталога никогда не перезаписываются и не удаляются при чтении.

`Store.publish` реализует только фиксацию подготовленных файлов. Построение индекса,
проверка его внутреннего формата и fsync/rename принадлежат будущему индексатору.
Читатель получает согласованные пары манифест/фрагменты одним SQL-снимком,
повторно проверяет хеши файлов перед загрузкой и fingerprint embeddings.
Для глобального ранжирования загрузчик собирает опубликованные шарды; BM25-статистики
должны вычисляться по всему видимому корпусу, оценки шардов нельзя просто склеивать.
Общий ready-снимок поиска закрепляется на время запроса; старые публикации сохраняются.

Первичный SQLite-каркас расширяется добавлением columns payload/active_publication
и таблицы publications. Старые строки не удаляются и не становятся автоматически ready
для нового читателя: им нужна повторная типизированная регистрация/публикация.
Низкоуровневые rows/execute оставлены для будущей очереди; они не являются путём публикации.

## План обработки вопроса

Исходный вопрос и максимум три подзапроса → BM25/FAISS по 30 кандидатов → RRF(60)
→ reranker до 40 уникальных фрагментов → условия/продолжения/подтверждённые поправки.
Дата as_of фильтрует подтверждённые периоды действия; неизвестная актуальность даёт
предупреждение. Более поздняя дата издания сама по себе не доказывает отмену.
Генерация Draft → структурная проверка и дословные цитаты → отдельный смысловой вызов
той же модели → максимум одно исправление → только проверенные выдержки при повторном сбое.
Смысловая проверка той же моделью не является независимым доказательством.

Без LLM: источники и поиск без придуманных утверждений. Без ML: BM25 с предупреждением,
манифест без векторов и последующая явная переиндексация. Отказ одного reranker при
доступных embeddings также переводит текущий ответ в консервативный BM25-режим.
При несовпадении fingerprint векторный поиск запрещён; явный BM25 допустим после
проверки его артефакта, без использования несовместимых векторов.
Между A100 и локальным компьютером автоматического переключения нет.

## Профили (плановые, аппаратно не проверены)

| PROFILE | LLM Q4_K_M | Контекст | Источники | Выход | Фрагменты | ML |
|---|---|---:|---:|---:|---:|---|
| a100 | Qwen2.5-14B-Instruct | 16384 | 8000 | 1536 | 8 | CUDA |
| 3060ti | Qwen3-8B | 4096 | 2200 | 768 | 4 | CPU |
| 4b | Qwen3-4B | 4096 | 2200 | 768 | 4 | CPU |
| development | Qwen3-4B, отключена | 4096 | 2200 | 768 | 4 | отключён |

PROFILE задаёт значения по умолчанию; явные настройки их переопределяют.
Источники + выход + резерв инструкций (по умолчанию 1024) ≤ контекст.
При реальном запросе дополнительно считать токены фактическим токенизатором:
сюда входят вопрос, JSON, инструкции и весь контекст, включая проверяемый черновик.
Один активный запрос к модели; generate/verify выполняются последовательно под общей
блокировкой всей цепочки. Qwen3 без thinking. Включение требует фиксации ревизий.
Начальная ревизия bge-m3 взята из каркаса и ещё требует проверки доступности весов.
4B выбирается вручную после проверки памяти/качества 8B; пригодность 3060 Ti не обещается.

Резервное копирование и перенос: остановить приложение, checkpoint SQLite WAL,
перенести всю DATA_DIR единым снимком и проверить хеши/fingerprint.
Реализация поиска, генерации, парсеров, HTTP routers и UI в эту основу не входит.

# Находки

Сгруппированы по зонам аудита. Префикс ID указывает зону: ING — обработка, CS — корпус/поиск, RAG-API — ответ/API, UI — интерфейс/безопасность, DEPLOY — развёртывание. Каждая находка помечена типом: подтверждённый дефект, противоречие документации или риск без воспроизведения.

## Обработка и OCR (`ingestion`)

### F-ING-1 — OCR отрывает колонку номеров пунктов от текста; документ публикуется как ready
Серьёзность: high. Тип: подтверждённый дефект + противоречие документации (`docs/ocr-review.md`: «Продолжения строк сохраняются внутри условия», «неоднозначные остаются needs_review»).
Требования: TZ-T1.1, TZ-T1.3, PRJ-01, PRJ-02, PRJ-03, TZ-DATA01.
Место: `navigator/ingestion/ocr.py:478` (`--psm 3`: Tesseract выделяет колонку номеров отдельным блоком/абзацем), `ocr.py:353-435` (`_layout_groups` обходит абзацы Tesseract по порядку блоков; строка из одного слова «1.1.» не считается номером, т.к. `number` требует `len(words)>1`, `ocr.py:367-369`; строки одного абзаца склеиваются через `same_par`, `ocr.py:411,415`), `pdf_parser.py:238-269` (каждая группа → отдельный Unit), `outline.py:12` (одиночный «1.1.» не матчится как пункт, «1.4. 1.5.» — матчится как пункт 1.4).
Воспроизведение: `<workdir>/work/ingestion/scripts/run_pdf.py` → `<workdir>/work/ingestion/fixtures/pdf/scan_rot0.pdf` (номер на x=70pt, текст на x=110pt, висячий отступ, 200 dpi); также `scan_wide.pdf`, `pdf2/scan_gap100.pdf`, `pdf2/scan_tnr300.pdf`; сквозь сервис — `run_service.py`.
Ожидаемое: юниты «1.1. Настоящий … сотрудникам.», section=1.1 и т.д. (так и получается для нативного PDF того же макета).
Фактическое: юниты `1.1.` | `1.2.` | `1.3.` | `1.4. 1.5.` (section=1.4) | затем пять абзацев текста без section. Опубликованный фрагмент `doc-…-f0001` (section «1.4», bbox только номера «1.1.» `[71.01,147.36,87.08,155.28]`): `"1. Общие положения\n1.1.\n1.2.\n1.3.\n1.4. 1.5.\nНастоящий искусственный регламент…"`. Статус документа `ready`, предупреждение только общее «Страницы распознаны OCR». Совпадает с симптомом на скриншоте пользователя (разрозненные «1.1. 1.2. … 2.1. 2.2.» плюс шапка). Воспроизводится во всех ориентациях 0/90/180/270 и для Arial/Times, 200/300 dpi; при узком зазоре (x=92pt) номера не отрываются.
Влияние: ссылка на конкретный пункт невозможна (section пустой или неверный), поиск по номеру пункта ведёт на «колонку номеров», ответ теряет привязку «пункт → условие»; ошибка не видна оператору, т.к. `needs_review=False`.
Направление исправления: в `_layout_groups` до группировки сопоставлять строки по вертикали между блоками Tesseract (одиночный токен-номер слева + строка текста с тем же baseline → одна строка), либо пробовать `--psm 4/6` для страниц с узкой левой колонкой номеров; если колонка номеров обнаружена, но не сопоставлена — `needs_review`. Добавить сквозной тест с настоящим Tesseract на искусственной странице с висячим отступом.

### F-ING-2 — Номера в отдельной колонке не перечитываются и искажаются без needs_review
Серьёзность: medium. Тип: подтверждённый дефект.
Требования: PRJ-03, PRJ-02, TZ-T1.3.
Место: `ocr.py:367-383` — перечитывание (`_reread_number`) и флаг «Номер пункта … не подтверждён» срабатывают только при `len(words)>1` и наличии текста справа в той же строке.
Воспроизведение: `run_pdf.py` — scan_rot0: «2.2.» → «22.»; scan_rot180: «1.3.» → «1:3:», «2.2.» → «р»; scan_rot270: «2.2.» → «йа.»; `run_pdf2.py` scan_tnr300: «22.».
Ожидаемое: исправление согласованным перечитыванием либо `needs_review` с предупреждением.
Фактическое: искажённые номера сохранены, `needs_review=False`, документ `ready`.
Влияние: неверные номера пунктов в опубликованном тексте; неоднозначность не показана человеку.
Направление: применять проверку номера к одиночным токенам левой колонки (геометрия + regex `\d[\d.:,]{1,12}` + соседи-номера), неподтверждённые → `needs_review`.

### F-ING-3 — Автонумерация Word (w:numPr) в DOCX теряется
Серьёзность: high. Тип: подтверждённый дефект (на искусственных данных; наличие автонумерации в реальных 8 DOCX не проверено).
Требования: TZ-T1.1, PRJ-03, TZ-DATA01.
Место: `navigator/ingestion/docx_parser.py:189-216` — текст абзаца берётся из `w:t`; `w:numPr`/`numbering.xml` нигде не читаются (поиск `numPr|numbering` по `navigator/` — 0 совпадений).
Воспроизведение: `run_office.py` → `fixtures/office/autonum.docx` (три абзаца стиля `List Number`).
Ожидаемое: «1. Первый пункт…», section=1, 2, 3 (или явная пометка, что номер вычисляется).
Фактическое: `'Первый пункт автонумерации.'` и т.д., section пустой, `needs_review=False`; через сервис — `ready` и опубликован.
Влияние: для документов с автоматической нумерацией невозможны ссылки на пункт и разделение по пунктам; ответ не может указать «п. 3.2».
Направление: вычислять номера по `numbering.xml` (abstractNum/lvl, lvlText, start, ilvl, сброс уровней) и подставлять в текст с пометкой источника; при неподдерживаемом формате — предупреждение и `needs_review`.

### F-ING-4 — Маркеры Wingdings остаются private-use символами; преобразование не учитывает шрифт
Серьёзность: medium. Тип: подтверждённый дефект.
Требования: PRJ-08.
Место: `docx_parser.py:17` (`_SYMBOL_MARKERS` — только F02D и F0B7, независимо от `w:font`), `docx_parser.py:39-43` (`w:sym` без учёта шрифта), `docx_parser.py:261-262`; PDF: `pdf_parser.py:21` (другая, тоже шрифтонезависимая таблица: F0A7/F076/F0D8/F0FC → «•»), `pdf_parser.py:29` (прочие PUA удаляются молча), `pdf_parser.py:146-149` (любая неизвестная PUA/`(cid:N)` отправляет всю страницу в OCR).
Воспроизведение: `run_office.py` → `fixtures/office/symbols.docx`.
Ожидаемое: «▪/•/➢/✓ Отдел закупок» (по шрифту), без PUA.
Фактическое: `' Отдел закупок (Wingdings F0A7)'`, `' …'`, `' …'`; документ `needs_review` с предупреждением «Нераспознанные символы шрифта». Публикация блокируется (безопасно), но частые маркеры Wingdings делают такие DOCX неготовыми, а в пакете проверки виден мусор.
Направление: таблица соответствий (шрифт, код) → Unicode для Symbol/Wingdings/Wingdings 2/3, общая для DOCX и PDF; неизвестные — сохранять и помечать, как сейчас.

### F-ING-5 — Группировка OCR склеивает заголовок с первым пунктом и продолжение пункта со следующим
Серьёзность: low. Тип: подтверждённый дефект (искусственные данные).
Требования: TZ-T1.1, PRJ-03.
Место: `ocr.py:409-415` (`same_par` объединяет строки одного абзаца Tesseract без проверки начала нового пункта, если номер не прошёл условие `number`).
Воспроизведение: `run_pdf2.py` — scan_gap92: юнит `"1. Общие положения 1.1. Настоящий …"` (section=1, пункт 1.1 потерян как отдельный), аналогично «2. Порядок … 2.1. …»; scan_tnr300: `"дежурный администратор корпуса. Решение направляется…"` (хвост 1.3 + текст 1.4 в одном юните).
Направление: начинать новую группу на строке, начинающейся с номера пункта, даже внутри абзаца Tesseract.

## Корпус, публикация, поиск (`corpus-search`)

### F-CS-1 — BM25 без морфологической нормализации русского языка
Серьёзность: high. Тип: подтверждённый дефект (качество поиска в BM25-режиме). Требования: TZ-T2.2, TZ-T2.3.
Место: navigator/rag/indexing.py:31-34 (`tokens`: только NFKC, casefold, ё→е), navigator/rag/retrieval.py:90-112.
Воспроизведение: `eval_bm25.py <repo> <work> reviewed` — 40 вопросов из docs/qa/questions.json на tests/fixtures/synthetic_corpus.json, реальные Indexer/Searcher, ML выключен.
Ожидаемое: цель docs/qa/README.md — Recall ≥ 0,90; перефразированный вопрос находит нужный пункт. Фактическое: recall@8 = 28/33 (0,85), recall@4 = 25/33 (0,76) на собственном наборе проекта. Промахи Q-G-S-03 («отменить» vs «Отмена»), Q-E-O-01 («оформление … пропуска» vs «Пропуск оформляется»), Q-E-O-02, Q-E-T-03, Q-G-C-06. Перефразы аудитора: 2/6.
Влияние: BM25 — режим по умолчанию (`ml_enabled=False`; профили development и laptop) и обязательный режим деградации; в нём не находятся пункты, отличающиеся только словоформой.
Направление: добавить лемматизацию или стемминг русского языка в токенизатор, поднять `TOKENIZER_VERSION`, переиндексировать; измерить на замороженной выборке без подгонки ожиданий.

### F-CS-2 — Декомпозиция составных вопросов не подключена
Серьёзность: medium. Тип: пробел реализации (подтверждён статически). Требования: TZ-T2.3, TZ-T5.2.
Место: navigator/rag/retrieval.py:121,139 принимает `Subqueries`; navigator/rag/pipeline.py:92-93 вызывает `search` только с исходным вопросом. Других производителей `Subqueries` в navigator/ нет.
Воспроизведение: grep по `Subqueries`/`subquer`; eval_bm25.py: в категории composite recall@4 = 3/7; составной вопрос аудитора из трёх частей теряет одну часть (`syn-pass-2-1-v1` вне top-8).
Ожидаемое: каждая часть составного вопроса получает свои основания. Фактическое: один общий запрос, части конкурируют за top-k (k=4 на профилях 3060ti/4b).
Направление: генерировать до трёх подзапросов (LLM или правила по союзам и вопросительным словам) и передавать их в `search`; проверить на вопросах категории composite.

### F-CS-3 — Один флаг reviewed=True превращает эвристические даты в фильтр редакций
Серьёзность: medium. Тип: риск, механизм воспроизведён на искусственных данных. Требования: TZ-T2.1, PRJ-12.
Место: navigator/ingestion/metadata_extractor.py:73 (`valid_from = … or issued`); navigator/documents/service.py:282-303 (PATCH сливает reviewed=True с имеющимися эвристическими полями); navigator/rag/retrieval.py:56-58.
Воспроизведение: `extract_metadata` для текста «Приказ № 5 от 01.02.2026» даёт `issued = valid_from = 2026-02-01`. В exp_review.py S4 после `patch_metadata(reviewed=True)` без изменения дат документ исчезает из выдачи на as_of 2026-02-15 (до PATCH был виден с предупреждением).
Ожидаемое: дата издания не равна дате вступления в силу (комментарий retrieval.py:71 это прямо фиксирует); подтверждение периода требует отдельного основания. Фактическое: эвристический `valid_from`, в том числе равный дате издания, становится «подтверждённым» вместе с флагом.
Направление: не заполнять `valid_from` датой издания или хранить эвристики отдельно от подтверждаемых полей; при reviewed=True требовать явных дат.

### F-CS-4 — Повреждение одного ready-шарда отключает поиск по всему корпусу
Серьёзность: low. Тип: риск доступности, воспроизведён. Требования: PRJ-13, TZ-T5.2.
Место: navigator/rag/retrieval.py:31-50 (`validate_lexical` для всех публикаций), :126-127.
Воспроизведение: exp_store.py S3c — правка bm25.json документа `a` в копии; запрос, относящийся только к документу `b`, получает `index_mismatch`.
Ожидаемое и фактическое: fail closed корректен и ничего не скрывает, но поиск по всем остальным документам тоже прекращается, а повреждённый документ не назван.
Направление: исключать повреждённую публикацию с явным предупреждением и диагностикой (или оставить как есть и документировать процедуру переиндексации).

### F-CS-5 — Публикация стартового корпуса не атомарна на уровне набора

### F-RAG-API-2 — `tests/test_model_clients.py::test_connection_refused` зависит от ОС: на macOS bound-but-not-listening сокет даёт timeout, а не RST
- Серьёзность: low. Тип: дефект теста (зависимость от окружения), не дефект кода.
- Требования: TZ-T5.3 (проверка классификации ошибок).
- Место: tests/test_model_clients.py:90-97. Код: navigator/rag/clients.py:84-90.
- Воспроизведение: тест прогнан 3 раза, каждый раз «1 failed» примерно за 5,2 с (ожидалось model_unavailable, получено model_timeout). `conn_probe.py`: connect к порту, который занят `bind()` без `listen()`, даёт `TimeoutError` через 5,0 с. И внутри песочницы, и без неё (`net.inet.tcp.blackhole=0`). К освобождённому порту — `ConnectionRefusedError(61)` за 0,000 с. `refused_transport.py`: `LocalTransport` на освобождённый порт → `model_unavailable`, retryable=True, 0,010 с; на bound-not-listening → `model_timeout`.
- Причина: в ядре XNU/BSD входящий SYN на сокет в состоянии TCPS_CLOSED отбрасывается без RST, а Linux отвечает RST. Комментарий теста «bound but not listening» предполагает поведение Linux. Песочница здесь ни при чём: поведение то же без неё.
- Ожидаемое/фактическое: код классифицирует ошибки корректно (refused → model_unavailable, timeout → model_timeout). Тест создаёт timeout вместо refused.
- Влияние: на macOS полный прогон всегда красный (466 passed / 1 failed) и на 5 с медленнее. Это маскирует реальные регрессии.
- Направление: эмулировать отказ детерминированно, например monkeypatch opener → `URLError(ConnectionRefusedError())`, или слушающий сокет с `SO_LINGER=0`, который сразу закрывает соединение. В тесте задать короткий timeout.
